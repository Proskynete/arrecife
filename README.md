# Arrecife

The component library of Eduardo Álvarez's visual identity.
`@eduardoalvarez/arrecife` · React 19 · TypeScript · shadcn/ui · Storybook · tsup.

Published Storybook: [arrecife.eduardoalvarez.dev](https://arrecife.eduardoalvarez.dev).

## The identity documents

`docs/design-system.md` and `docs/brand-manual.md` are the extraction of the two
Claude Design canvases, kept in the repo so they can be grepped and versioned.
The canvas is still the source; this is the consultable copy.

They are here for a concrete reason: the highlighting palette lived hand-written
in a project with a `#E05252` that this README has declared wrong for months, and
nobody saw it because the document was not greppable from the code.

`docs/decisions.md` is the other half: the points where the code and the document
do not say the same thing, each with its resolution and its reason.

## The two documents for agents

`AGENTS.md` is for an agent working **in this repo**: how a component is created,
which rules it cannot break and where each one is verified. `CLAUDE.md` is a
symlink to that file, so Claude, Codex and Cursor all read the same text.

`llms.txt` is for an agent working in one of the **five projects that consume**
the library. That agent never sees this repo: it sees
`node_modules/@eduardoalvarez/arrecife/`, which is why `llms.txt` travels in the
tarball and is declared in `exports`.

The component and prop inventory in `llms.txt` is not written by hand:
`scripts/build-llms.mjs` extracts it from the TypeScript compiler, and
`pnpm check:llms` fails in CI if somebody changes a prop and does not regenerate
it. The prose lives in `docs/llms.template.md`. It is the same decision as the
tokens: one source, a generated output, and a check that stops them disagreeing.

## The constraint that outranks everything else

`src/tokens/` imports nothing: not React, not components, not third-party CSS. It
is the only subpackage the five projects can all consume, including an OG
generator running on Satori and an Astro site that mounts no React. The moment a
token depends on a component, the library has stopped being portable.

It is not documentation: `pnpm check:tokens` verifies it on every build and
ESLint says so in the editor.

## Tailwind output

One source, `src/tokens/tokens.ts`. One generated output,
`dist/tokens/theme.css`, with `@theme` for Tailwind v4. It is generated by
`scripts/build-tokens.mjs`; it is not edited by hand and it is regenerated on
every build.

Phase 0 decision: **v4 only**. The portfolio (`eduardoalvarez.dev`) migrates from
Tailwind v3 to v4 before consuming Arrecife. If that migration slips, publishing
the v3 preset again is one more emitter in `build-tokens.mjs` reading the same
`tokens` object: the source does not change.

### Consuming it

```css
@import "tailwindcss";
@import "@eduardoalvarez/arrecife/tokens/theme.css";
```

Dark mode is primary and it is the default. A project in light mode declares
`data-theme="light"` on `<html>`; a dark one declares nothing.

**If you are also going to use components, one line is missing, and without it
nothing fails.** Tailwind does not scan `node_modules`, so it purges every class
the components emit: `border-hairline`, `rounded-pill` and `p-step-lg` resolve to
nothing. There is no console error, no build warning, no undefined class — the
card simply comes out with a `currentColor` border and the pill comes out square.

```css
@import "tailwindcss";
@import "@eduardoalvarez/arrecife/tokens/theme.css";

/* Without this, the components mount with none of the system's styles. */
@source "../node_modules/@eduardoalvarez/arrecife/dist";
```

The path is relative to the CSS file the directive lives in, so in a project with
the sheet in `src/styles/` it goes up two levels and not one. The blog's E2E
tests caught it, not the build, and until 0.3.0 this was only written in
`llms.txt` — the file an agent reads and a person does not.

### `npx arrecife` — the two things that fail without saying so

```
npx arrecife
```

It reads your stylesheets and checks the two failures that produce no error, both
of which cost real hours in the migration:

**The missing `@source`**, above. It also works out the path for you, counted
from the sheet and not from the project root, which is the part that gets written
wrong.

**A token of yours redefining one of ours.** A project coming from shadcn brings
`@theme inline { --color-accent: var(--accent); }`, and the two are not the same
colour: shadcn's `--accent` is the hover **surface**, `#17303E`, and this
library's is the brand turquoise, `#35D6C0`. The result was **88 classes inside
the library's own components** painting grey — 28 `text-accent`, 26 focus rings,
15 `bg-accent`, 12 `border-accent`. Buttons, focus rings and badges came out the
colour of a surface and it looked as though the migration had done nothing. (The
twenty-six are one `focus-ring` utility now, which changes the count and not the
failure: it reads `var(--color-accent)` like everything else here.)

```
arrecife · 2 thing(s) that fail without saying so:

  src/styles/globals.css
    imports @eduardoalvarez/arrecife/tokens/theme.css and has no @source.
    Every class the components emit is being purged — silently. Add:

      @source "../../node_modules/@eduardoalvarez/arrecife/dist";

  src/styles/globals.css
    redefines --color-accent, which @eduardoalvarez/arrecife owns.
      yours:    var(--accent)   ← points at another property, so it wins silently
      arrecife: #35D6C0
```

Five names collide with shadcn's — `background`, `border`, `warm`, `warm-hover`
and `accent`. Four are harmless because both sides happen to agree on the value,
so the command reports the value on each side and only fails on the ones that
differ. A collision that agrees is worth knowing about and is not worth failing
over.

>
> Everything else is additive, and most of it lets a project delete something it

>

The font families are declared by name. Each project loads Bricolage Grotesque,
Geist and JetBrains Mono however it prefers: the library does not dictate how.

**The names have to match EXACTLY**, and this has already bitten twice. The
tokens declare the families like this:

| Token | `font-family` it declares | Utility |
| --- | --- | --- |
| `fonts.display` | `"Bricolage Grotesque"` | `font-display` |
| `fonts.sans` | `"Geist"` | `font-sans` |
| `fonts.mono` | `"JetBrains Mono"` | `font-mono` |

A project registering its `@font-face` as `"Bricolage Grotesque Variable"` or
`"Geist Variable"` — the name several font packages publish them under — is
**not** loading what the tokens ask for: the display and the mono fall back to
the system font, silently and with no console warning. It is exactly what
happened in two of the five projects.

The `@font-face`'s `family` is an alias the project chooses, so the fix is to
declare it with the name the token asks for:

```css
@font-face {
  font-family: "Bricolage Grotesque"; /* NOT "Bricolage Grotesque Variable" */
  src: url("/fonts/bricolage-grotesque.woff2") format("woff2-variations");
  font-weight: 200 800;
  font-display: swap;
}
```

#### In Next, with `next/font`

It is the same failure through another door, and it bites both Next projects.
`next/font` registers each family under a GENERATED name — `__Geist_a1b2c3` — and
exposes it as a custom property; the literal `"Geist"` the tokens declare exists
in no `@font-face` on the page.

Importing `theme.css` overwrites `--font-sans` with that literal, and all three
families fall back to the system font. Silently: there is no 404, because the
font did load — under another name.

The fix is to reassert all three AFTER the import, pointing at the variables
`next/font` generates:

```ts
// app/fonts.ts
import { Geist, Bricolage_Grotesque, JetBrains_Mono } from 'next/font/google';

export const sans = Geist({ subsets: ['latin'], variable: '--project-sans' });
export const display = Bricolage_Grotesque({ subsets: ['latin'], variable: '--project-display' });
export const mono = JetBrains_Mono({ subsets: ['latin'], variable: '--project-mono' });
```

```css
@import "tailwindcss";
@import "@eduardoalvarez/arrecife/tokens/theme.css";
@source "../node_modules/@eduardoalvarez/arrecife/dist";

/* After the import, or the literal that is not loaded wins. */
@theme {
  --font-sans: var(--project-sans), ui-sans-serif, system-ui, sans-serif;
  --font-display: var(--project-display), ui-sans-serif, system-ui, sans-serif;
  --font-mono: var(--project-mono), ui-monospace, SFMono-Regular, Menlo, monospace;
}
```

The variables are called `--project-*` and not `--font-*` on purpose:
`--font-sans` is the name Tailwind uses for ITS token, and handing it to
`next/font` leaves the two layers fighting over the same property.

Each family's `variable` goes on the `<html>` class, as Next asks:
`className={`${sans.variable} ${display.variable} ${mono.variable}`}`.

The `light:` variant is available for the inverted light-mode cases.

The object can also be consumed in JS, with no CSS and no React — it is what the
OG templates use:

```ts
import { tokens } from '@eduardoalvarez/arrecife/tokens';
```

The highlighting theme lives in another subpath for the same reason — it is
consumed from `astro.config.mjs`, not from a component:

```ts
import { arrecife } from '@eduardoalvarez/arrecife/shiki';

export default defineConfig({
  markdown: { syntaxHighlight: 'shiki', shikiConfig: { theme: arrecife } },
});
```

**The library does not ship Shiki.** The projects already highlight at build time
with their own tooling; what they were missing was not a highlighter, it was the
theme. `CodeBlock` still receives the code already highlighted, which is what it
is written for.

The OG templates are published in their own subpath for the same reason: a
generator runs in a worker or in a build script and must not drag in React or a
single component.

```ts
import satori from 'satori';
import { articleTemplate, OG } from '@eduardoalvarez/arrecife/og';

const svg = await satori(articleTemplate({ title, date, readingMinutes }), {
  width: OG.width,   // 1200
  height: OG.height, // 630
  fonts: [...],
});
```

They are pure functions returning the tree Satori paints, built only from tokens.
`dist/og/index.js` mentions React on no line, and that is checkable with a grep.

## How it is used from a project

```tsx
import { Text, Button, Badge, cn } from '@eduardoalvarez/arrecife';
import type { TextProps } from '@eduardoalvarez/arrecife';

<Text variant="eyebrow" tone="muted">charlas</Text>
<Text as="h2" variant="h1">Escalar con criterio</Text>
<Text variant="body">Clamps itself to 68ch.</Text>
<Text variant="ui" measure={false}>No clamp, for a narrow cell.</Text>
```

Every component publishes its documentation page in Storybook with the props
table generated from the types. `Text`'s:

| prop | type | default |
| --- | --- | --- |
| `variant` | `display · stat · h1 · h2 · h3 · body · lead · ui · label · tag · meta · chip · eyebrow` | `body` |
| `tone` | `primary · secondary · muted · accent · warm · success · warning · error` | `primary` |
| `as` | `h1 · h2 · h3 · h4 · p · span · strong · em · figcaption · caption · legend · dt · dd · li` | per `variant` |
| `measure` | `boolean` — clamps to 68ch | `true` on `body` |
| `asChild` | `boolean` — renders the child, to wrap a link | `false` |

Verified by packing the library with `pnpm pack` and installing it in a separate
project: the types resolve from `dist/`, `./tokens` loads without dragging React
in and `./tokens/theme.css` resolves by subpath.

### The social icons come from `./social`

```tsx
// ❌ does not exist: the root publishes them grouped, not loose
import { GitHub, LinkedIn } from '@eduardoalvarez/arrecife';

// ✅ the normal form
import { GitHub, LinkedIn } from '@eduardoalvarez/arrecife/social';

// ✅ for iterating the catalogue
import { social } from '@eduardoalvarez/arrecife';
<social.GitHub />
```

All nine are `GitHub`, `LinkedIn`, `X`, `Instagram`, `Discord`, `YouTube`, `Rss`,
`Email` and `Newsletter`.

**The two forms are not taste, and in Next they are not interchangeable.** The
root carries `"use client"`, and what crosses into a Server Component is a client
reference **per export** — the properties of a plain object are not exports. So
from a Server Component `social.LinkedIn` is `undefined`, and `undefined` as an
element type kills the build at prerender. `./social` carries no directive: the
icon renders on the server, ships no client JS, and pulls 5.6 KB instead of the
root's 116 KB. Reach for the subpath by default; reach for `social` when you are
mapping a list of link names onto icons.

The namespace stays because **one of them is called `X`**. An `export const X` at
the root of a component library collides with anything — a generic's type
variable, an `import { X }` from somewhere else — and the failure shows up far
from here. In the subpath you asked for icons, so the collision is yours to
resolve and it takes one word: `import { X as XIcon }`.

`Newsletter` is the bell, and it is named for what it means and not for what it
draws — same as everything else in the system. It plays `Rss`'s role: a way to
follow, not a social network. That is what keeps it inside this catalogue and
keeps the catalogue from turning into an icon library.

**The internal glyphs are NOT exported.** `Close`, `ChevronDown`, `Copy`, `Sun`
and company are the minimum set the primitives need and they stay inside.
Publishing them would turn `lib/glyphs.tsx` into the icon library the system
decided not to have, and from there it grows on its own. A project that needs an
icon passes its own: `Stat` receives `icon`, `Footer` receives each social link's
`icon`.

### The icons are yours, the way they are drawn is not

That last sentence used to end there, and «its own what, drawn how» had no
answer. The admin panel imports 89 distinct icons in 229 places — 77 of them
domain icons for a course admin, which no design system was going to ship — and
drew them at `size-4` twenty-six times, plus `size-3.5`, `size-3`, `size-6` and
`size-7`, with no rule behind any of them.

```tsx
import { GraduationCap } from '@phosphor-icons/react';
import { Icon } from '@eduardoalvarez/arrecife/icons';

<Icon as={GraduationCap} />
```

1em, so the icon takes the size of the text it sits in and nobody picks a number.
Weight `regular` by default, and **that is the whole reason the set is
Phosphor**: it bakes the weight into the path instead of exposing a
`strokeWidth`, and its regular lands on the one stroke the identity document
names. Measured on the `Minus` path itself, whose regular form is a bar of radius
8 on a 256 grid:

| | Line | As a fraction of the rendered size |
| --- | --- | --- |
| phosphor `regular` | 16 on a 256 grid | **0.0625em** |
| the document | 1.6 on a 24 grid | **0.0667em** |
| `lib/glyphs.tsx` | 1.75 on a 16 grid | 0.109em |

Six per cent apart, which is no pixel on any screen. Nothing had to be derived and
no number had to be invented. The `Icons/Icon` → `regular IS the document's
stroke` story alternates the bars so the claim can be checked instead of believed
— and it also shows the third row, because **`glyphs.tsx` is the outlier**: at
0.109em it is three quarters heavier than both, it was never argued anywhere, and
aligning it would restyle every primitive in the library. That is a separate
change and `docs/decisions.md` § 29 says so.

**The weight is an axis with three values, and `tone` is how you name them.**
`weight` is not a prop: Phosphor ships six and this system reads three, because
`thin`, `bold` and `duotone` have no role behind them here.

| `tone` | Weight | What it is |
| --- | --- | --- |
| `action` · the default | `regular` | An icon that is a control or names one |
| `current` | `fill` | The one of a set you are on — the item carrying `aria-current` |
| `quiet` | `light` | Furniture: a marker in a metadata row, not a control and not a state |

`current` is the value that earns the axis, and the argument is not taste.
An active sidebar item already says so in biolume, and **colour on its own is the
one channel WCAG 1.4.1 says may not carry meaning** — the fill is the second
channel, and it is the one that survives a forced-colours mode where the biolume
does not. `quiet` is the opposite problem: in a metadata row the icon is not the
point of the line, and at `regular` it draws as heavy as the date beside it.
`docs/decisions.md` § 35 has the rest.

`@phosphor-icons/react` is an **optional** peer dependency on its own subpath, by
the same rule as `./form` and `./chart`: two of the five projects use no icons and
install nothing.

**An icon is not illustration.** Tiburoncín — the faces, the poses, the fin — is
the mascot, it comes from `./brand`, and the manual doses it by surface: a face
only in an empty state, a confirmation, an error, course progress or a
celebration. An icon is functional vocabulary and goes wherever a control needs a
label it cannot spell. Adopting a set changed nothing about the first, and
neither stands in for the other in either direction.

**In Next, import from `@phosphor-icons/react/ssr` inside a Server Component.**
Phosphor's default build reads `IconContext` through `useContext`, and a hook in a
Server Component throws — and it ships no `"use client"` to stop you, so the
failure arrives at render. The `/ssr` entry is the same icons without the context
read, and `Icon` works with either.

### `"use client"` is in the published `dist`

The root, `./brand`, `./form` and `./chart` carry the directive. They render
React, and their Radix primitives call `createContext` at module scope: without
it, a Next project with the App Router cannot import the library at all — it
fails at build time with `TypeError: (0 , r.createContext) is not a function`.
It blocked `cursos` for a whole version, and the workaround there was a
`"use client"` in every one of that project's own adapters, including a `Badge`
that is a `<span>` with no interaction. It cost 272 KB of client chunk.

The five portable subpaths do NOT carry it — `./tokens`, `./theme`,
`./variants`, `./og` and `./shiki` — and that is the half that matters more.
Marking them client would be a lie with a cost: a Server Component importing
`buttonVariants`, a function that returns a string, would pull a client boundary
in with it.

`./social` is the third case, and it is why the check stopped looking only at the
portable ones. It renders React — it is nine `<svg>` — so it can never be
portable, and it holds no state, so it must not be a client entry either. Listed
in neither set, nothing would have noticed it being marked client by mistake, and
that mistake undoes the only reason the subpath exists. See `docs/decisions.md`
§ 26.

It is stamped by `scripts/add-use-client.mjs` after tsup, and not by tsup's
`banner`. That was tried first: esbuild writes the directive and the bundling
pass strips it back out with a `Module level directives cause errors when
bundled` warning. The build stayed green and the published package was broken for
Next — the worst way to fail, because the failure surfaces in somebody else's
project. `check:exports` now verifies it in both directions: present on the four
client entries, absent from every other subpath.

It is inert outside Next. In Astro and in plain Vite it is a string literal at
the top of a module; Rollup may warn and nothing else happens. One `dist` serves
the Next projects and the Astro ones, which is the constraint that decided the
shape.

### `./variants` — the class vocabulary without React

```ts
import { buttonVariants, badgeVariants, CARD_SURFACE }
  from '@eduardoalvarez/arrecife/variants';
```

`buttonVariants`, `badgeVariants` and `categoryBadgeVariants` are not
components: they are functions that return a string of classes. They touch
neither React nor the DOM. They used to live inside the components, so importing
one dragged the whole library along, and that had a cost measured in two of the
five projects.

In `cursos` it forced a `"use client"` on an adapter whose entire content was one
call to CVA. In `links`, which depends on no React at all, it was not even an
option: that project copied the class vocabulary by hand into `LinkRow.astro` and
`Footer.astro`, and the copy had already drifted once — the hero gradient sat at
`55%` and `#e9eeea` against the token's `60%` and `#EFE9DE`, and nothing compared
them.

The rule for what belongs in the subpath: if it returns classes, it goes there;
if it returns markup, it stays in the component. `Button` renders a `<button>`,
so it stays at the root; `buttonVariants` returns a string, so it is in
`./variants`. The root re-exports all of it, so an existing
`import { buttonVariants } from '@eduardoalvarez/arrecife'` keeps working — what
the subpath buys is not the name, it is not paying for React to get it.

### The two subpaths that ask for a dependency

`./form` and `./chart` do not hang off the root, and that is deliberate. Each
asks for an **optional** peer dependency — `react-hook-form` and `recharts` — and
hanging them off the main index would force all five projects to install them so
their bundler could resolve an import four of them never execute.

It is the same decision as `./og` and `./shiki`, seen from the other side: there
React is kept out of the way of whoever does not mount it; here Recharts is kept
out of the way of whoever does not draw.

```tsx
import { Form, FormField, FormItem, FormLabel, FormControl, FormMessage }
  from '@eduardoalvarez/arrecife/form';

import { ChartContainer, ChartTooltip, ChartTooltipContent, seriesColor }
  from '@eduardoalvarez/arrecife/chart';
```

`check:exports` verifies that the five portable ones — `./tokens`, `./theme`,
`./variants`, `./og` and `./shiki` — bring no React into the published `dist/`,
**by following the relative imports**. Without that the check was worthless: with `treeshake`
on, each portable entry ends up as two lines re-exporting from a
`chunk-XXXX.js`, and a grep over those two lines finds no React even when the
chunk imports it.

## Contrast as a test, not as a panel

`pnpm test` mounts every story in a real Chromium and runs axe over it with
`a11y: { test: 'error' }`. It runs twice, once per mode: a color only fails in
one of the two, so passing in dark proves nothing about light.

It is demonstrably not decorative: putting light `textMuted` back to its previous
value takes down eight stories with «insufficient color contrast of 4.24».

There is exactly one disabled rule, in two specific stories and with the reason
written beside it: `aria-hidden-focus` on open `Select`/`DropdownMenu`. Radix
marks everything outside the portal `aria-hidden` and leaves the trigger inside
it still focusable; focus is trapped by its `FocusScope`, so it cannot be tabbed
to. It is a known disagreement between axe and Radix.

## Contrast corrections

The identity document measured everything against `background`. But
`surfaceRaised` is the worst case in **both** modes: in light it is darker than
the page background, in dark it is lighter. It is where menus and active tabs
live.

| token | before | now | reason |
| --- | --- | --- | --- |
| `light.textMuted` | `#6B7480` | `#626A75` | 4.24 did not reach AA over paper |
| `light.warning` | `#9A6A12` | `#8D6111` | 4.23 did not reach AA over paper |
| `dark.error` | `#E05252` | `#E15757` | 4.35 over `surface`, which is where a form error goes |

All three keep their exact hue and saturation: only lightness moves, by one to
four points. Light `accent` and `warm` are untouched.

New token: `hairlineHover` — `#2C4D5D` in dark (rule 6's value) and `#D3C8B2` in
light, derived by matching the perceptual step (ΔL\* 10.5) rather than the
contrast ratio, which overshoots near white.

`textMuted` never goes over `surfaceRaised`: in dark it gives 4.07. Menus use
`textSecondary`, which gives 6.96.

### The third correction: a semantic color is not a text color over its own tint

It came up while implementing the document's alert recipe — background at 8 % of
the semantic color — and the suite took it down in light mode, across five
stories.

The light semantics are calibrated to pass **just** over paper. Tinting the
background with them sinks them below AA:

| tone | over paper | over its own 8 % tint | `textPrimary` over the tint |
| --- | --- | --- | --- |
| `accent` | 4.55 | **4.12** | 14.82 |
| `warm` | 4.54 | **4.11** | 14.85 |
| `success` | 5.80 | 5.17 | 14.63 |
| `warning` | 4.88 | **4.40** | 14.78 |
| `error` | 4.87 | **4.35** | 14.64 |

No alpha fixes it: the problem is putting the color on top of itself. The
resolution does not touch the palette — the tint is a **surface**, so the text on
top of it is a text token. The semantic color stays where it is not text: the
border and the glyph.

The 8 %, incidentally, holds up as well as or better over paper than over abyss
(1.106 vs. 1.149 in accent). The suspicion that light mode needed a second table
ran the other way round: the system's weak point is `error` over abyss, 1.067.

## Publishing a version

**There are no manual steps.** The tag, the CHANGELOG and the version bump are
done by release-please from the conventional commits that already get written —
and that `lint-pr-title` already forces to be written correctly.

The whole cycle lives in `.github/workflows/release.yml`:

1. You merge a PR to `main` with a title like `feat(badge): …`.
2. release-please opens — or updates — a PR called `chore: release X.Y.Z` with
   the bump in `package.json` and the new `CHANGELOG.md` entry. That PR stays
   open and accumulates with every merge, so you can group several changes into
   one version.
3. When you merge it, it cuts the tag, creates the release and triggers the
   publish.
4. Before uploading anything, the workflow checks that the tag and `package.json`
   match, and runs lint, types, build, the `exports` verification and the full
   suite in both modes.
5. With the package already on npm, it builds Storybook and deploys it to
   [arrecife.eduardoalvarez.dev](https://arrecife.eduardoalvarez.dev).

`feat:` bumps the minor and `fix:` the patch. While the version is `0.x`, a
breaking change bumps the **minor** and not the major: that is what the `0.`
means — that the API can still move without spending 1.0. It is in
`release-please-config.json`, and `initial-version` with the first release's
`0.1.0` is there too.

When the API stabilises, it goes up to `1.0.0` by hand once, and from then on a
`BREAKING CHANGE:` bumps the major like in any other package.

### How release-please decides what to cut

Two pieces of information, and they come from different places. Knowing this
avoids the one failure that leaves the release stuck:

| Datum | Where it comes from |
| --- | --- |
| The **version** | From the PR **title** — `chore(main): release 0.2.0` |
| The **component** | From the **branch name** — `release-please--branches--main--components--arrecife` |

The component is derived from `package.json` and **cannot be pinned by
configuration**: there is no `component` key in the
[official schema](https://raw.githubusercontent.com/googleapis/release-please/main/schemas/config.json).
`include-component-in-tag: false` is what makes the tag `v0.2.0` and not
`arrecife-v0.2.0`.

If the title or the branch are edited by hand and stop matching, release-please
does not create the release and every run ends in `There are untagged, merged
release PRs outstanding - aborting`. There is no way out of that through
configuration: the tag and the release have to be cut by hand and the PR
relabelled `autorelease: tagged`.

`pnpm check:release` validates the configuration against that schema on every CI
run. It exists because release-please **silently ignores** keys it does not know:
an invented option raises no error, shows in no log and does nothing.

### Trusted publishing

The workflow publishes with **OIDC**: GitHub issues a token proving «this build
came out of this repo and this workflow», and npm exchanges it for permission to
publish. There is no long-lived secret to steal, or to rotate. It also generates
**provenance**, which signs the package with a verifiable link to that exact
commit.

It is configured once, on npmjs.com → the package → *Settings* → *Trusted
publisher*:

| Field | Value |
| --- | --- |
| Publisher | GitHub Actions |
| Organization or user | `Proskynete` |
| Repository | `arrecife` |
| Workflow filename | `release.yml` |
| Environment | `npm` |

That *Workflow filename* is the reason the release and the publish live in a
single file rather than in a reusable workflow: npm matches the token against a
name, and with `workflow_call` there are two candidates.

**The chicken and the egg.** You cannot configure a trusted publisher on a
package that does not exist yet, so the first version needs a token:

1. Create the `npm` environment in the repo settings with the `NPM_TOKEN` secret
   (an *automation* token).
2. Bump the version and publish for the first time. The workflow says in the log
   that it is using a token.
3. Configure trusted publishing with the table above.
4. **Delete the `NPM_TOKEN` secret.** The step that uses it skips itself when it
   is absent, and OIDC takes over without touching a line of the workflow.

To test without spending a version: *Actions → Release y publicación → Run
workflow* with the dry run enabled. It does everything but publish, needs no
token, and the run summary lists which files would travel and how big the tarball
is.

The dry run **does deploy Storybook**, to a Vercel preview and not to the public
domain. That is deliberate: a dry run that skips a job cannot tell you whether
that job works, and the deploy was the only step in the workflow that could not
be tested without spending a version.

One detail of the dry run that is confusing the first time: `npm publish
--dry-run` queries the registry, and `package.json` points at an **already
published** version except in the window between release-please bumping the
number and the workflow publishing. So the dry run runs into `cannot publish over
the previously published versions` over the one thing that cannot be right in a
dry run. That specific message is forgiven with a notice; any other failure still
fails.

### Storybook is deployed with the version

The published Storybook is the library's documentation: every story is both the
example and the test that verifies it. It lives at
[arrecife.eduardoalvarez.dev](https://arrecife.eduardoalvarez.dev) and it is
uploaded by `release.yml`'s `deploy` job, **after** npm has published.

That order is not an implementation detail. The site and the package have to tell
the same version: a Storybook ahead of npm shows components nobody can install
yet, and that is exactly the failure this repo exists because of — one source of
truth drifting from another.

Hence the decision that surprises people: **the Vercel project is not connected
to GitHub.** With the Git integration, Vercel builds on its own on every push to
`main` and there is no way to ask it to wait for the tag. The only thing that
deploys is the workflow, and it uploads Storybook **already built**: with the
Build Output API and `--prebuilt`, Vercel executes nothing, it serves what is in
`.vercel/output/static`. That way it is built by the same Node and the same
lockfile that just verified the library.

It is configured once, with `vercel link` in a local clone to create the project
and get the two ids out of `.vercel/project.json`. **Careful with one extra
step:** `vercel link` connects the GitHub repository to the project on its own
and without asking, which is exactly what you do not want. It is undone with
`vercel git disconnect`, and it is worth checking before calling the project
configured.

| Where | Name | What it is |
| --- | --- | --- |
| *Secrets* | `VERCEL_TOKEN` | A Vercel account token |
| *Variables* | `VERCEL_ORG_ID` | The `orgId` from `.vercel/project.json` |
| *Variables* | `VERCEL_PROJECT_ID` | The `projectId` from `.vercel/project.json` |

The two ids go in as **variables** and not as secrets on purpose: they are not
secret — they come out of any clone that runs `vercel link` — and as variables
they are readable in the log when something does not add up.

The team's deployment protection is `all_except_custom_domains`: each deploy's
unique URL asks for a team session and returns a 302 to the login, and the public
one is the custom domain. It is not a misconfiguration, it is Vercel's default
and it is the one we want.

**If they are missing, the job warns and does not break.** By the time it runs,
npm has published and the tag has been cut: a red there would read as «the
release failed», which is the opposite of what happened. The warning stays in the
run summary.

### `Hero` and `NewsletterForm` came back in

They were off the list with a written argument, and the argument was revisited.

**`Hero`.** It had been ruled out because «the portfolio's hero and the courses
one are the same skeleton as a section header, and `PageHeader` covers them with
a scale prop». That holds for the text and only for the text. The document's hero
also has a gradient, a panel radius, text clamped to 62 % of the width and the
pose bleeding off the bottom-right corner — none of which fits in a `PageHeader`
scale prop, and all of which are identity rules that get reimplemented five times
if they do not live here. They are two different pieces: `PageHeader` is still
the section header and goes inside `<main>`; `Hero` is the cover and there is one
per site.

**`NewsletterForm`.** It had been ruled out because «half its code is a `POST` to
an endpoint that only lives there: that is infrastructure». Correct, and that is
why the `POST` is not here. The component is presentational: it takes `state` and
emits `onSubmitEmail`, and the project makes the call with its own provider. What
IS identity are the four states and, above all, that the notice goes **below**
the form instead of replacing it — replacing it is what breaks the real case of
somebody who subscribes with the wrong email.

`Nav`, `Footer`, `Breadcrumb` and `Hero` are page composition and can be argued
about as library pieces. They get in anyway: the CLI aesthetic — the bar's
`./section`, the path's `~ / artículos / slug`, the footer's `$ cd ~/…` signature
— is the first thing that drifts when five projects each write it on their own.

### Phase 3 decisions

- **It ships no icon set**, and that has not changed. The eight glyphs the
  primitives need are inline in `src/lib/glyphs.tsx`, inherit `currentColor` and
  measure 1em, and they are not exported. What DID change is that
  `@phosphor-icons/react` is now an optional peer on `./icons`, so the set a
  project chooses is drawn at the system's weight — see «The icons are yours»
  above. Optional and on a subpath is the point: the two projects that use no
  icons install nothing.
- **No entrance animations.** Modals, menus, tooltips and toasts appear where
  they will stay. The `Switch` knob changes position without sliding. The
  system's only transition is `transition-standard`, which can only animate color
  and border because that is how the utility is written.
- **One exception, documented:** the `Button loading` spinner spins. A loading
  button with no movement is indistinguishable from a disabled one; it is
  feedback about progress, not about state, and it is wrapped in `motion-safe`.
- **`Progress` requires `label`.** A bar with no accessible name does not say
  what the progress is about, and no other part of the component can deduce it.
- **Zero literal hexes**, `Button` included. Rule 2 comes out as
  `light:bg-brand-hull`, because the hull was already a token.
- **Explicit `cursor-pointer`** on everything you press. Tailwind v4 removed
  `cursor: pointer` for `button` from the preflight, so a button without the
  class keeps the system arrow. It is carried by `Button`, `Checkbox`,
  `RadioGroupItem`, `Switch`, `TabsTrigger`, `Select`'s trigger, the close
  buttons of `Dialog`/`Sheet`/`Toast`, `PaginationLink`, the shell of the
  clickable cards and the links in `Nav`, `Footer` and `Breadcrumb` — which
  render an `<a>` with no `href` when a router's `Link` is plugged into them.

  Two deliberate exceptions. `Label` points at a control but is not the control.
  And the **menu items** of `Select` and `DropdownMenu` stay on `cursor-default`:
  a native menu does not show the pointing hand, and the row highlight already
  says the row responds.

### The syntax palette

Straight from the document: «keywords sand, strings biolume, comments plankton,
identifiers foam», over hull. Four colors on purpose — functions, variables and
types all land on foam, because the system communicates with color and border and
not with chromatic noise. Numbers and booleans ride with strings: the document
does not assign them, and grouping them under «they are literals» is more
coherent than introducing a fifth color.

Measured over `brand.hull` #0B1524, all AA:

| role | token | contrast |
| --- | --- | --- |
| identifier | `textPrimary` | 16.42:1 |
| literal | `accent` | 10.05:1 |
| keyword | `warm` | 9.05:1 |
| comment | `textMuted` | 5.43:1 |
| invalid | `error` | 4.97:1 |

`brand.body` (#3E7CB1) is not in it: the system restricts it to fill and here it
measures 4.2:1.

It used to live hand-written in
`eduardoalvarez.dev/src/settings/shiki-reef.ts`, and a `#E05252` had been left
inside it — precisely the hex this README says is wrong. It is the textbook case

`tokens.syntax` and the red comes out corrected on its own.

### Nestable themes

`theme.css` emits one block per mode, not just the light one. That way a subtree
can declare the opposite mode to the page and everything inside honours it.

`CodeBlock` uses it: `brand.hull` is «the background of code blocks», so a block
is dark in light mode too — and there `textPrimary` is nearly black. The block's
root declares `data-theme="dark"` and the ink resolves itself. It is the system's
only island of inverted theme, and it is deliberate.

### The cards and rule 6

`ArticleCard`, `TalkCard`, `CourseCard` and `LinkRow` share an internal shell
that is not published, so rule 6 lives in exactly one place: the hover changes
the border from `hairline` to `hairlineHover` and tints the title with accent.
Nothing else.

`LinkRow` comes from `links/src/components/Card.astro`, which scaled the card to
102 %, lifted the title by a pixel and rotated and enlarged the icon — four
movements the system does not allow.

No card depends on a router: by default they render an `<a href>`, and `asChild`
lets Next's or Astro's `Link` be plugged in.

### `AudioPlayer` — what changed on migration

The logic was not rewritten. The three modes, the floating player, the ±15s
skips, the 1 → 1.25 → 1.5 → 1.75 → 2 speed cycle and the volume with mute are the
portfolio's. What changed:

**Two dependencies a package cannot have.** The portfolio's `Icon` became
`src/lib/glyphs.tsx` with identical paths; `trackEvent` became the `onFirstPlay`
prop, which still fires exactly once per load.

**One API change.** `compact`/`banner` as two booleans became
`mode="full" | "compact" | "banner"`, which is the vocabulary the three modes were
already described with. The portfolio's call sites need touching in Phase 6.

**Three animations the system does not allow.** The waveform no longer animates
`scaleY` — the bars still tell playback from pause by opacity. The floating
player appears and disappears instead of sliding. The progress bar no longer
interpolates its width, which also made it lag behind the audio. The loading
spinner's spin stays, with the same justification as in `Button`.

**An inherited contrast failure.** The speed button put `textMuted` over
`surfaceRaised`: 4.07:1 in dark. It moved to `textSecondary`. The original still
carries that failure.

**A latent bug.** The player's pieces live at module level, not inside the
component. Declared inside, they change identity on every render and React
remounts them: with `timeupdate` firing four times a second, dragging the bar
lost pointer capture.

### The fifth motion exception: the footer's caret

The CLI signature ends in a block caret that blinks, behind `motion-safe`. It is
the first exception that is not feedback about progress, so it needed a different
argument.

The signature is a **prompt** — that is why it is mono, why the `$` is in accent
and why it sits in a footer instead of a `<p>` saying «© 2026». A prompt whose
caret does not blink is a terminal that has hung, and a still block at the end of
a line reads as a stray character.

So the criterion splits in two. The first four exceptions are feedback about
progress or spatial continuity; this one is legibility: it is not decoration, it
is what makes the piece readable as what it is. `step-end` and not a fade,
because a real caret is on or off and easing it turns a terminal into a pulsing
dot. See `docs/decisions.md` § 23.

### The second motion exception

`Sheet` slides. It is the second and last exception to «no displacement»,
approved knowingly: a panel entering from an edge, held still, would be an
off-centre modal. It lasts `--duration-standard` with `--ease-standard` — the
same time and the same curve as any color change — so it introduces no new
timing, and it sits behind `motion-safe`.

`Calendar` does **not** animate the month change: react-day-picker's `animate`
stays on its default, which is off.

### The danger variant, and where it does not go

`Button` has `destructive` and `destructiveOutline` since 0.6.0. For four
versions it had neither, on an argument that is still half right: inside an
`AlertDialog` the confirm button is **not** red, because a title explains what is
about to happen, focus starts on cancel and clicking outside does not close it.
The context does the work and a red button on top of it is shouting.

What broke the argument is the table row. `cursos` has eight destructive buttons
in row actions and toolbars, next to «Editar» and «Duplicar», with nothing around
them doing that work — and rendered as `secondary`, «Eliminar curso» looked
exactly like «Cancelar».

The palette is not `error`, and the reason is the role. `error` is a text color:
it reads against a dark surface, so it sits mid-red. `danger` is a fill: what
reads is the ink on top of it, so it goes lighter. Same split as `accent` and
`accentOn`. In light mode both land on `#C0392B`, because over paper a red dark
enough to carry white ink is also the red that reads as text.

| | dark | light |
| --- | --- | --- |
| ink over fill | 6.53 | 5.11 |
| ink over hover | 7.92 | 6.61 |
| fill over background | 6.71 | 4.87 |
| fill over surfaceRaised | 4.91 | **4.50** |

That last cell is exactly on the AA line, which is where every light semantic in
this palette sits. It matters because it is the outline variant's border and
text, and `surfaceRaised` is where a toolbar lives.

`destructiveOutline` fills on hover, and that is a declared exception to
«secondary is never filled» — a destructive that looks identical to a secondary
until you read it is the problem the variant exists to fix. See
`docs/decisions.md` § 21.

### `icon-sm`, for the one admin app

42×42 is the right measure for a control you hit with a thumb, and four of the
five projects are reading sites where that fits. `cursos` is the odd one out:
three actions per table row, and at 42 the row grows with them.

`size="icon-sm"` is 32×32, and it is 32 and not the 28 that project actually had:
32 is `sm`'s height, so a dense icon button lines up with a small text button and
a toolbar mixing the two stays on one baseline. It does not replace `icon` — a
page's primary action stays at 42. See `docs/decisions.md` § 22.

### The theme script, and the mode a site already decided

```astro
<script is:inline set:html={themeScript({ base: 'dark' })} />
```

Until 0.6.0 `themeScript` was a fixed string and resolved stored choice →
`prefers-color-scheme` → dark. That is the right default for a library, and it
was wrong for all five of these projects: they are dark BY DECISION, and
`eduardoalvarez.dev`'s own script said so out loud — «dark is the brand's PRIMARY
mode, so it's the default and doesn't follow the OS setting». With the OS in
charge, a reader whose machine is in light mode saw the blog in light.

There was no way to say otherwise, so those projects kept their own
`public/theme.js` and the library published the hard part for nobody. Migrating
just the button did not help either: `ThemeToggle` persists under
`arrecife-theme` and their script read `theme`, so the two would have gone out of
step.

`base` stops the OS from being consulted at all. A stored choice still wins over
it — it sets what happens when nobody has chosen yet, not what happens instead of
choosing, so the toggle keeps working.

### `Text` — the scale as API

`Text` was not on the original list and was added later, because without it the
scale only existed as loose classes and nothing stopped anyone putting
`text-display` on a paragraph. Three of the system's rules live inside the
component:

| rule | how it is applied |
| --- | --- |
| display for headlines only, never body | the family is bound to the scale; no `font` prop exists |
| weight and tracking belong to the scale | they come from the `--text-*` token and are not exposed |
| maximum body measure 68ch | `body` applies it on its own; `measure={false}` removes it |

`as` and `variant` are independent on purpose: a second-level heading that has to
look smaller is `<Text as="h2" variant="h3">`, not an `h3` that lies about the
page hierarchy.
